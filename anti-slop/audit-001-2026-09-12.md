Scope: source inspection, existing executable tests, computed contrast. This is an audit report, not a new UI delivery or full visual certification. No live desktop click-through was performed. Findings based on source are distinguished from measured evidence.

Direction: Windows utility, black/white palette, multiple layouts, movable edge dock and user-adjustable opacity. These are explicit user choices, not slop. Audit interpretation: ENERGY 1 / RHYTHM 1 / MOTION 1. Preserve the quiet utility design; no decorative redesign needed.

## Numbered findings

1. **HIGH: Low opacity also fades text and controls. R-25, R-34.**
   Evidence: `src/Widget.cs:105` sets Window.Opacity, including foreground text; `src/Widget.cs:266` permits 20%. At 20%, black text over a white desktop becomes #CCCCCC on #FFFFFF (1.61:1). White text over a black desktop becomes #333333 on #000000 (1.66:1). Both fail even the large-text threshold. Ratios computed using the skill's contrast-check.py. These are compositing calculations, not sampled screenshots. This does not establish a failure at the default 70%.
   Fix: preserve the requested adjustable transparency for the resting tab; offer an opaque/readable panel during hover and keyboard focus, or separate background opacity from content and enforce a tested contrast-safe surface. Do not silently remove the user's opacity preference.

2. **HIGH: Collapsed dock and movement lack keyboard equivalents. R-32.**
   Evidence: `src/Widget.cs:58` expands on MouseEnter. The collapsed handle at lines 122–127 is a TextBlock with only a mouse drag handler, not a focusable button. Dragging is handled through mouse capture. The only explicit keyboard handler is Escape. Tray "Buka widget" uses Show/Activate without expanding. Thus activating the collapsed window does not provide a keyboard route into its controls. Collapse also ignores keyboard focus at line 63.
   Fix: focusable dock button, Enter/Space to expand, arrow-key movement along the selected edge, Shift+F10 for settings, and no auto-collapse while focus is inside the panel.

3. **HIGH: Refresh destroys focused controls. R-32, C-4.**
   Evidence: `src/Widget.cs:114` clears the entire panel. Refresh calls Render before and after each request (lines 316 and 329), and checks/rendering can also run in the background. A focused button is removed and replaced; there is no focus preservation or restoration. This is a source-established removal of focus targets, not a recorded keyboard session.
   Fix: retain the visual tree and update bound values/states. At minimum preserve logical focus and defer structural rendering during interaction. Verify keyboard focus through a full automatic refresh.

4. **HIGH: Usage fetch lacks explicit loading feedback. R-27.**
   Evidence: `src/Widget.cs:316` sets busy and renders without updating status. The buttons become disabled through line 98, while existing text/values remain. Initial load can still say "Log masuk" while checking an existing session. Manual update checks likewise have no visible checking state. Downloading an update does have a loading label; this finding concerns usage/account fetch and update checking.
   Fix: show "Menyemak akaun…", "Mengemas kini baki…" or "Menyemak update…" as appropriate, with a status announcement for assistive technology. Keep last-success time distinct from in-progress status.

5. **MEDIUM: Diamond glyph has no stated product meaning. R-04.**
   Evidence: `src/Widget.cs:122` and `src/Widget.cs:133` use the generic diamond glyph as product decoration. No purpose or requested icon direction is documented. The real update arrow is functional and is not included in this finding.
   Fix: use the product name alone, or retain a motif only with a clear documented meaning. This is a small visual cleanup, not grounds to change the black/white theme or utility layout.

6. **HIGH: Interaction/theme delivery evidence is incomplete. R-35.**
   Evidence: `verification/Program.cs` instantiates an unshown Widget, changes private preferences, invokes Render and raises a synthetic MouseEnter. It does not run a live pointer drag, keyboard navigation, theme-menu interaction, delayed collapse, real updater download or MSI upgrade/relaunch. The opacity test checks the numeric property, not readability. Prior release notes correctly disclosed the untested interactive upgrade.
   Fix: record live checks of both themes, each layout/dock edge, keyboard/focus, loading/offline states, opacity over representative backgrounds, and successful/cancelled update flows. This is a coverage gap, not a claim that every untested feature is broken.
